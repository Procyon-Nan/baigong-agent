## 1. 阶段目标

P2 在 P1 应用骨架上建立两条彼此独立的认证入口，并将它们归一为同一套服务端授权上下文：

1. 本地入口：供本项目独立验证和调试，支持本地普通用户与管理员通过用户名或邮箱加密码登录。
2. 嵌入入口：供任意已登记宿主系统为其已认证用户申请受控的短期嵌入会话。

P2 同时交付最小用户管理、最小嵌入接入管理、服务端 RBAC、账号状态检查、会话撤销、登录保护和相关审计。P3 的对话接口必须直接复用 P2 形成的统一身份与授权接口。

本文件的 Better Auth 选型取代 P1 完成文档中“P2 再接入 Auth.js”的阶段性占位说明；P1 已完成的代码与验收结果不因此改变。

## 2. 范围边界

### 2.1 P2 范围

- Better Auth、Drizzle Adapter、PostgreSQL 数据库会话和 Argon2id 密码哈希。
- 本地登录、退出、首次修改临时密码和本地会话管理。
- 初始管理员交互式初始化命令。
- 固定 `USER`/`ADMIN` 角色、账号状态和统一服务端授权入口。
- 最小用户管理页面与 API。
- 通用嵌入客户端、一次性票据、嵌入会话、续期轮换和撤销协议。
- 最小“嵌入接入”管理页面与 API。
- PostgreSQL 登录限流、失败计数和 P2 安全操作审计。

### 2.2 不在 P2 范围

- 自助注册、邮箱验证、SMTP、找回密码和自定义角色编辑器。
- OAuth、OIDC、SAML、DG IAM 或任何特定宿主身份系统适配。
- 本地身份与嵌入身份的合并、绑定、转换或自动关联。
- P3 对话链路、P4 完整会话审计、P7 完整管理体验和 P9 可复用嵌入组件。
- 修改 `baigong-platform` 或其他宿主项目。宿主方后续自行适配本项目公开协议。
- Redis、外部身份提供商或应用多副本并行运行支持。

## 3. 技术选型与运行环境

### 3.1 依赖版本

- Better Auth `1.6.25`。
- Better Auth Drizzle Adapter，连接现有 Drizzle ORM `0.45.2` 和 PostgreSQL。
- Better Auth Username Plugin，支持用户名登录。
- Better Auth Bearer Plugin，仅用于受控嵌入会话通过 `Authorization: Bearer` 调用应用接口。
- `@node-rs/argon2` `2.0.2`，通过 Better Auth 自定义密码哈希接口使用 Argon2id。
- 现有 Next.js `16.2.12`、React `19.2.8` 和 Node.js 24。

不再采用 Auth.js。P2 不引入 Redis、SMTP、OAuth/OIDC 服务、宿主 IAM SDK 或其他外部基础设施。

### 3.2 实施所需环境

开始实现和验收前需具备：

- WSL/Linux、Node.js 24 和 npm。
- 可创建表、索引和约束的 PostgreSQL 连接，并已执行 P1 迁移。
- P2 数据库和 HTTP 验收必须显式配置 `P2_TEST_DATABASE_URL`，且其数据库不得与 `DATABASE_URL` 相同。验收脚本未配置独立测试库时立即拒绝运行，不允许回退到应用数据库。
- 可写的项目数据目录。
- 浏览器，用于本地 Cookie 会话与跨 Origin iframe 协议验收。
- 嵌入联调时使用两个明确 Origin：Agent 应用 Origin 和模拟宿主 Origin。生产协议只允许 HTTPS；开发可显式登记 `http://localhost:<port>`。
- `BAIGONG_APP_ORIGIN`：应用唯一公开 Origin。生产必须使用精确 HTTPS Origin；仅 `localhost`、`127.0.0.1` 或 `[::1]` 可用于生产模式本地验收的 HTTP 例外。
- 若经反向代理部署，代理必须覆盖客户端提供的 `X-Real-IP`；应用只以该头实施来源限流，绝不接受 `X-Forwarded-For`。不得将可伪造 `X-Real-IP` 的应用端口直接暴露给公网。

P2 不依赖已配置模型、模型 API Key、S3、真实知识库系统或 `baigong-platform`。身份与权限验收不得因这些服务缺失而阻塞。

### 3.3 项目数据目录基线

数据目录严格遵循提交 `2655c3abe3839074c013b3a5d9a3f35b45ebe9d7` 确立的规则：

- WSL 开发可使用项目根目录下的 `.data`。Windows 挂载无法可靠呈现 Unix 权限是已接受的开发环境例外，不构成阶段阻塞。
- 生产 `BAIGONG_DATA_DIR` 必须是 Linux 原生文件系统上的绝对路径。目录必须持久化、不可通过 Web 访问、不进入 Git，并由应用运行用户独占。
- 生产目录权限为 `0700`，密钥文件权限为 `0600`；容器部署必须挂载持久卷，部署、升级和清理流程不得删除该目录。

Better Auth 认证密钥通过现有 `src/server/config/data-directory.ts` 的密钥加载抽象首次自动生成并持久化，不存入数据库，也不提供环境变量配置。它必须与 `credential-encryption.key` 和 `jwt-signing.key` 使用不同文件和独立随机材料。P2 不另建第二套数据目录解析或密钥文件权限逻辑。

## 4. 身份与授权模型

### 4.1 统一身份上下文

本地 Cookie 会话和嵌入 Bearer 会话在认证后均转换为服务端只读的 `AuthenticatedPrincipal`。至少包含：

```ts
type AuthenticatedPrincipal = {
  userId: string;
  tenantId: string;
  role: "USER" | "ADMIN";
  source: "LOCAL" | "EMBEDDED";
  sessionId: string;
  integrationId: string | null;
};
```

该对象只能由已验证的数据库记录构造。请求体、查询参数、Header、Prompt 或 Tool 参数中的内部 `userId`、`tenantId`、`role` 和 `source` 均不得覆盖它。

### 4.2 数据库权威状态

- PostgreSQL 会话记录、应用用户资料和嵌入客户端状态是授权权威。
- 每次敏感管理操作必须重新读取当前用户状态和角色。
- P3 及后续所有会话操作必须通过统一授权接口校验租户、账号状态和资源所有权。
- 浏览器导航隐藏仅用于体验，不构成授权。页面、Route Handler、Server Action 和服务函数均执行服务端检查。

### 4.3 固定角色

- `USER`：只能访问自己有权使用的资源。
- `ADMIN`：可访问本租户管理功能，并按 P0 规则查看或取消其他用户会话。
- 嵌入用户固定为 `USER`，任何客户端请求均不能将其提升为 `ADMIN`。
- 首版只有默认租户，但所有用户、会话、客户端和审计记录仍显式携带 `tenant_id`。

## 5. 本地账号与会话

### 5.1 账号规则

- 本地普通用户和管理员共用一个登录页，不提供角色选择器。
- 登录标识为用户名或邮箱加密码。
- 每个本地账号必须同时具有用户名和邮箱；两者去除首尾空白并规范化为小写后分别保持唯一。
- 不开放自助注册，不执行邮箱验证，不依赖 SMTP。
- 密码至少 12 个字符，不强制大小写、数字或符号组合。
- 密码使用 Argon2id 哈希。明文密码不得进入数据库、日志、审计、命令参数、环境变量或进程列表。

### 5.2 本地会话

- Better Auth 使用 HttpOnly Cookie 和 PostgreSQL 数据库会话。
- 会话为 7 天滚动有效期。用户持续使用时可持续续期，不设置绝对最长时限。
- 允许同一用户保持多个并发会话，首版不限制设备数量。
- 用户被禁用、密码被管理员重置或角色发生变化时，立即撤销该用户全部现有会话。
- 管理员可显式撤销指定用户全部会话。
- 本地 Cookie 写操作执行同源与 CSRF 防护。

### 5.3 初始管理员

实现 `npm run admin:bootstrap` 交互式一次性命令：

- 交互输入用户名、邮箱和显示名称，不提供默认值。
- 生成高强度随机临时密码并只在成功创建后显示一次。
- 密码不得作为命令参数或环境变量输入。
- 已存在有效本地管理员时失败关闭，不创建第二个初始化管理员。
- 新管理员首次登录后必须先修改临时密码，才可执行其他业务操作。

## 6. 登录保护

开发和生产统一使用 PostgreSQL 持久化限制状态：

- 同一来源最多请求登录端点 3 次/10 秒。
- 同一规范化用户名或邮箱在 15 分钟内连续失败 10 次后，该标识限制登录 15 分钟。
- 成功登录后清除该标识的连续失败状态。
- 不存在、禁用、密码错误和受限账号返回同类通用错误，不泄露账号存在性、状态或内部限制原因。
- 登录成功、失败和触发限制均写入审计，但不记录密码、密码哈希或完整会话令牌。
- 嵌入客户端认证使用独立限流桶，不与本地登录共享计数。

同一标识的失败计数更新和限制判断必须使用可并发安全的数据库操作，不能仅保存在单进程内存中。

## 7. 用户管理

P2 提供最小管理员页面和 API：

- 列出本地用户和嵌入用户，显示身份来源、状态、角色和最后登录时间。
- 创建本地 `USER` 或 `ADMIN`，生成仅显示一次的临时密码。
- 启用或禁用账号。
- 调整本地用户的 `USER`/`ADMIN` 角色。
- 重置本地用户密码，生成仅显示一次的临时密码并要求首次登录修改。
- 撤销指定用户全部会话。
- 查看和禁用嵌入用户；不得为其设置密码、改变身份来源或授予管理员角色。

用户记录首版不提供硬删除。禁用或降级操作不得导致系统不存在有效本地管理员；该不变式必须通过事务内数据库检查保护，不能只由页面按钮状态保证。所有用户管理操作均写入审计。

## 8. 通用嵌入认证协议

### 8.1 信任边界

- 本项目只识别自己签发的 `client_id + client_secret`、一次性票据和嵌入会话。
- 本项目不读取、不依赖也不识别宿主的 IAM、数据库、角色模型或内部 API。
- 宿主后端负责先确认其用户仍已登录，再以客户端凭据调用本项目。
- 长期 `client_secret` 只存在于宿主后端。创建或轮换时明文只显示一次，本项目数据库仅保存哈希。
- 每个客户端配置精确允许的 Origin。禁止 `*`、子域通配和模糊匹配；生产只允许 HTTPS，开发允许明确登记的 localhost Origin。

### 8.2 一次性票据

宿主后端申请票据时提交稳定的 `external_user_id`、目标 Origin，以及可选显示名称和展示邮箱。票据：

- 使用密码学安全随机值，数据库仅保存不可反推原值的摘要。
- 绑定 `integration_id`、`external_user_id`、精确 Origin、主 Agent、随机 `jti` 和过期时间。
- 有效期为 120 秒。
- 通过单条条件更新或事务锁定实现一次性原子消费；过期、已消费、客户端停用或 Origin 不匹配时失败关闭。
- 不放入 URL。宿主页面通过限定 `targetOrigin` 的 `postMessage` 将票据交给 iframe。

首次成功兑换票据时，以 `integration_id + external_user_id` 自动创建嵌入影子用户。后续兑换复用该身份。

### 8.3 嵌入会话

- 票据兑换后创建 60 分钟的 PostgreSQL 数据库会话，并通过 Better Auth Bearer Plugin 接受 Bearer 会话令牌。
- 会话令牌只保存在 iframe JavaScript 运行内存中，不进入 URL、Cookie、`localStorage` 或 `sessionStorage`。
- iframe 刷新后必须由宿主重新申请票据，不能从浏览器持久化恢复令牌。
- 嵌入会话不能自行刷新。宿主页面存续且宿主确认用户仍已登录时，其后端每 15 分钟申请新票据并交给 iframe。
- 成功续期时签发新令牌并立即使旧令牌失效。持续得到宿主续期时不设置绝对最长时限。
- 宿主退出或关闭嵌入功能时应尽力立即撤销当前会话；未成功撤销时，60 分钟到期是最终失效边界。
- 停用或删除客户端立即撤销其全部未消费票据和有效会话。禁用嵌入用户立即拒绝新票据兑换和续期，并撤销其现有会话。

### 8.4 永久身份隔离

本地用户与嵌入用户在首版及所有后续版本中均不得合并、绑定、转换或自动关联：

- `integration_id + external_user_id` 是嵌入身份唯一稳定键。
- 相同用户名、邮箱或显示名称不产生任何身份关系。
- 不提供手工合并入口，也不预留未来自动合并行为。
- 嵌入用户没有本地密码，不能使用本地登录页。
- 宿主邮箱是可选、可重复、可变更的展示资料，不参与认证或找回。
- Better Auth 内部必需的唯一邮箱字段对嵌入用户使用系统生成、不可登录的内部标识；该字段不得显示为用户资料或参与本地登录查找。
- 宿主可在成功续期时更新显示名称和展示邮箱，但不能改变 `external_user_id` 或身份来源。

## 9. 嵌入接入管理

P2 提供最小“嵌入接入”管理员页面和 API：

- 创建客户端并仅一次显示 `client_secret`。
- 查看客户端名称、`client_id`、启用状态、精确允许 Origin 和更新时间，不回显密钥。
- 修改精确允许 Origin。
- 停用、启用或删除客户端。
- 轮换客户端密钥；新密钥创建成功后旧密钥立即失效。
- 所有创建、修改、启停、删除和密钥轮换操作均写入审计。

P7 可扩展管理体验，但不得改变本协议的信任边界。P9 负责可复用 iframe 组件、完整协议文档和接入示例，不实现特定宿主适配。

## 10. 数据模型边界

最终表名以 Better Auth `1.6.25` Schema 生成结果和项目现有命名规范为准，但职责必须保持清晰：

| 数据职责 | 最小字段或约束 |
| --- | --- |
| Better Auth 用户、会话、账号、验证与限流表 | 使用 Drizzle Adapter 的当前版本 Schema；数据库会话可撤销、可查询过期时间并关联用户 |
| 应用用户资料 | `user_id`、`tenant_id`、`source`、固定角色、状态、显示名称、可选展示邮箱、`must_change_password`、最后登录时间 |
| 本地登录标识 | Better Auth 用户名与登录邮箱均规范化为小写并分别唯一，只供本地身份登录；嵌入身份不占用本地登录名，内部生成邮箱也不进入登录查找 |
| 外部身份 | `integration_id + external_user_id` 复合唯一，关联一个且仅一个嵌入用户 |
| 嵌入客户端 | 租户、名称、不可预测 `client_id`、密钥哈希、状态和精确允许 Origin |
| 一次性票据 | 票据摘要、客户端、外部用户、Origin、主 Agent、`jti`、到期与消费时间 |
| 嵌入会话关联 | Better Auth 会话、客户端、嵌入用户、到期与撤销状态，用于按客户端批量撤销 |
| 登录失败限制 | 规范化标识摘要、窗口、连续失败次数和限制截止时间 |
| 审计记录 | 租户、操作者、动作、目标、结果、时间和必要的非敏感元数据 |

应用用户资料与 Better Auth 用户记录保持一对一。涉及用户、角色、状态、票据或批量会话撤销的写操作必须在单个数据库事务中维护约束。

## 11. 模块与依赖方向

实现时遵循以下边界，具体文件可按现有目录命名细化：

```text
app/                         页面和 Route Handler，只负责协议适配
src/server/auth/             Better Auth 配置、会话解析和统一 principal
src/server/authorization/    RBAC、账号状态、租户与资源权限断言
src/server/users/            本地/嵌入用户应用服务与仓储
src/server/integrations/     客户端、票据、兑换、续期与撤销
src/server/audit/            P2 审计写入接口
src/server/db/schema/        只定义持久化结构和约束
scripts/                     交互式初始管理员命令
```

- 页面和 Route Handler 不直接拼接跨表权限查询。
- Better Auth 回调只处理认证框架边界，不承载完整用户管理或嵌入业务。
- 授权层依赖统一 principal 和仓储接口，不依赖 React、页面组件或宿主系统类型。
- 本地与嵌入入口共享授权层，但凭据验证、会话生命周期和身份映射保持独立。
- 禁止建立指向 `baigong-platform` 的源码依赖、共享数据库依赖或网络 API 依赖。

## 12. 实施顺序

1. 安装并锁定 Better Auth、Drizzle Adapter 相关能力和 `@node-rs/argon2`，根据实际 `1.6.25` API 建立最小配置测试。
2. 定义应用用户、认证、限流、嵌入与审计 Schema，生成并验证版本化迁移。
3. 扩展现有数据目录密钥抽象，生成独立 Better Auth 认证密钥；接入数据库会话和 Argon2id。
4. 建立 `AuthenticatedPrincipal`、固定 RBAC、账号状态和最后有效管理员保护。
5. 实现 `admin:bootstrap`、本地登录、退出、首次改密、会话撤销和登录保护。
6. 实现最小用户管理服务、API 和页面。
7. 实现嵌入客户端、票据兑换、60 分钟 Bearer 会话、15 分钟宿主续期轮换和撤销。
8. 实现最小嵌入接入管理服务、API 和页面。
9. 完成单元、数据库集成、路由和浏览器验收，再进入 P3。

每一步优先复用 P1 的数据库、配置、数据目录、错误处理和应用框架；不得建立职责重复的并行实现。

## 13. 验收标准

### 13.1 自动化检查

- `npm run build`、`npm run typecheck`、`npm test`、`npm run db:check` 全部通过。
- `npm run test:p2:database` 与 `npm run test:p2:http` 只使用 `P2_TEST_DATABASE_URL`。每次运行生成随机测试标识，并在结束时清理该次运行创建的租户、用户、会话、客户端、票据、审计和限流记录。
- 在空 PostgreSQL 数据库执行全量迁移成功，在已完成 P1 迁移的数据库增量迁移成功。
- Argon2id 哈希、用户名/邮箱规范化、通用登录错误、来源限流和标识连续失败限制有自动化测试。
- 用户禁用、密码重置、角色变化、客户端停用/删除和密钥轮换均验证旧会话或旧密钥立即失效。
- 最后有效本地管理员保护有事务级并发测试。
- 票据过期、重复消费、Origin 不匹配和并发兑换均失败关闭。
- 本地用户与嵌入用户同邮箱或同显示名称时仍保持两个独立身份。

### 13.2 浏览器与协议验收

- 本地 `USER` 与 `ADMIN` 使用同一登录页，且不能由浏览器选择或篡改角色。
- 临时密码首次登录必须改密；改密前不能进入其他业务页面。
- 普通用户访问管理页面或 API 返回服务端拒绝。
- 仅登记的精确 Origin 可兑换嵌入票据；嵌入用户固定为 `USER`。
- 票据和 Bearer 令牌不出现在 URL、浏览器持久化存储、日志或错误响应中。
- iframe 刷新需要新票据；续期成功后旧令牌失效；宿主停止续期后会话最迟在 60 分钟后失效。
- 生产配置拒绝非 HTTPS 的非 localhost Origin。

### 13.3 阶段完成条件

- P2 的本地和嵌入两条认证链路均可独立验收。
- 所有 P2 页面和 API 共用统一服务端 principal 与授权规则。
- P2 安全操作均形成不含敏感明文的审计记录。
- 当前源码和文档不依赖或修改任何特定宿主系统。
- P3 可以直接基于 P2 的身份上下文实现会话所有权与安全对话链路，无需重新设计认证。

## 14. 实施结果

P2 已按本文件实现。核心实现位于以下模块：
